\section{Benchmark Model and System Architecture}
\label{sec:benchmark_model}

Marine Race Arena combines four architectural elements: a declarative race
configuration, a set of participants and their autonomy interfaces, a
race-management and evaluation layer, and a simulator adapter. This separation
defines the benchmark independently of both the controller implementation and
the simulation backend. A race can therefore be reconfigured without changing
the autonomy code, while a new controller or vehicle can be connected without
changing the race definition or adjudication logic.

\subsection{Benchmark Instance}

\noindent\textbf{Definition~1 (Benchmark instance).} A \mra{} instance is
defined by the tuple

\begin{equation}
\label{eq:instance}
\mathcal{E} =
(\mathcal{W},\mathcal{G},\mathcal{S},\mathcal{F},
 \mathcal{C},\mathcal{O},\mathcal{P},\mathcal{R}),
\end{equation}

where:

\begin{itemize}

\item $\mathcal{W}$ is the simulation world and navigable volume;

\item $\mathcal{G}=(g_1,\dots,g_M)$ is the ordered gate sequence;

\item $\mathcal{S}$ defines the starting conditions, including participant
spawn and release settings;

\item $\mathcal{F}$ defines the race finish condition;

\item $\mathcal{C}$ represents the environmental current field;

\item $\mathcal{O}$ is the set of obstacles in the scenario;

\item $\mathcal{P}=\{1,\dots,N\}$ is the participant set, with each participant
associated with a vehicle, sensor profile and controller;

\item $\mathcal{R}$ contains the race and referee configuration, including
validation criteria, penalties, timeouts and scoring rules.

\end{itemize}

The tuple is a conceptual description of the benchmark instance. Its concrete
values are supplied by the declarative track and race configuration and are
interpreted by the configuration loader, arena builder and simulator adapter at
run time.

\subsection{Runtime Architecture}

The runtime lifecycle begins with the track and race configuration. A
configuration loader and validator checks the declarative input and constructs
an arena through the arena builder. The builder creates the configured scenario
and connects it to the selected simulator adapter. The resulting arena instance
is then handed to the race runner, which is the central component during
execution. This configuration pipeline and the runtime components are shown in
Fig.~\ref{fig:runtime_architecture}.

\input{figures/architecture_diagram}

During a race, the runner advances the execution and coordinates all
participants. For each participant, it obtains the information exposed through
the participant interface and passes it to that participant's controller. The
controller returns a vehicle command to the runner, which forwards it through the
adapter so that the simulator and vehicle can apply it. The same participant
cycle is executed independently for every vehicle in the race.

In parallel, the referee receives the evaluation data required to adjudicate the
configured race. It determines official progression and rule outcomes, records
events and penalties, and produces participant results. These evaluation results
are not sent back to the controller and do not form a feedback path into
autonomy. At the end of the run, the race manager emits machine-readable
summaries and structured event logs. In a multi-vehicle race, the same scheme is
applied separately to each participant, while the race manager can additionally
compute the configured team-level result.

Fig.~\ref{fig:schematic_boundary} presents the complementary conceptual view.
The participant/autonomy flow carries the information available to the
controller and the resulting vehicle command, whereas the race-evaluation flow
uses referee-side data to determine official outcomes. The two flows meet in the
race manager for execution and reporting, but evaluation does not close a
feedback loop toward the controller.
